02แอปพลิเคชันใช้ AI ทำอะไร

📝 ตรวจเรียงความ (Essay Grading)

วางเรียงความ → เลือก Rubric (ทั่วไป / เชิงโต้แย้ง / Pitch Deck) → AI ให้คะแนนแยกรายเกณฑ์ พร้อมคอมเมนต์และ Feedback รายบุคคล

🧾 ตรวจข้อสอบปรนัย (Quiz Grading)

วางโจทย์ MCQ + คำตอบนักเรียน → AI วิเคราะห์และสร้างเฉลยพร้อมคำอธิบายรายข้อ → ระบบเทียบคำตอบและคำนวณคะแนน

🤖 โมเดลที่ใช้

Qwen 3.8 Max ผ่าน OpenAI-compatible API · เรียกผ่าน local proxy (Python) — API key ไม่ผ่านเบราว์เซอร์

✨ กลไกจริยธรรมที่ฝังในตัวแอป (ไม่ใช่แค่สไลด์)

  • Transparency panel — แสดง prompt จริงที่ส่งให้ AI ทุกครั้ง
  • Anti-Hallucination — ทุกคะแนนต้องแนบข้อความยกตรง (quote) จากตัวงาน
  • Consistency Check — ตรวจงานเดิม 3 รอบ แสดงส่วนต่างคะแนน
  • Teacher Override + Audit Log — มนุษย์แก้คะแนนได้ ต้องระบุเหตุผล ระบบบันทึกทุกครั้ง
  • Demo Mode ติดป้ายชัดเจน — ผลลัพธ์จำลองไม่แอบอ้างเป็น AI จริง

▶ การสาธิตสด

รัน python3 serve.py → เปิด localhost:8000 → วางเรียงความตัวอย่าง → กดตรวจ → ดูคะแนนรายเกณฑ์ + evidence → กด Consistency Check ให้ดูคะแนนแกว่งจริง → แก้คะแนนด้วย Teacher Override → เปิด Audit Log

03ประเด็นจริยธรรม AI ที่พบในแอปของเรา (วิเคราะห์เชิงลึก — ไม่ใช่แค่ระบุหัวข้อ)

⚖️ Bias / Fairness

โมเดลภาษาฝึกจากข้อมูลภาษาอังกฤษ/ไทยกลางเป็นหลัก → ลำเอียงต่อสำนวนของนักเรียนที่ไม่ใช่เจ้าของภาษา หรือใช้ภาษาท้องถิ่น งานที่ "เขียนสวยตามขนบ" อาจได้คะแนนสูงกว่างานที่เนื้อหาลึกแต่ภาษาง่าย — ให้รางวัลกับสไตล์ ไม่ใช่สาระ

🎭 Hallucination / Accuracy

ผลทดสอบจริงตอนพัฒนา: AI เคยอ้างว่าพบคำสะกดผิดจำนวนมากในงานที่สะกดถูก และให้คะแนนไวยากรณ์ต่ำโดยไม่มีหลักฐาน — ถ้าครูไม่ตรวจ นักเรียนถูกตัดคะแนนฟรี

🔍 Transparency

คะแนนเป็น black box — นักเรียนไม่รู้ว่าถูกหักคะแนนเพราะอะไร อุทธรณ์ไม่ได้ ถ้ามองไม่เห็นเกณฑ์และเหตุผล

🔒 Privacy (PDPA)

เรียงความ/ข้อสอบอาจมีข้อมูลส่วนบุคคลของนักเรียน (ข้อมูลผู้เยาว์ = ข้อมูลอ่อนไหวตามกฎหมาย) การส่งไป API ภายนอก = เปิดเผยข้อมูลให้ผู้ให้บริการโดยผู้เรียนไม่เคยยินยอม

🧑‍⚖️ Accountability

ถ้า AI ให้คะแนนผิดจนนักเรียนเสียสิทธิ์ — ใครรับผิดชอบ? ครูที่กดปุ่ม? ผู้พัฒนาแอป? หรือผู้ให้บริการโมเดล? ปัจจุบันไม่มีกฎหมายระบุชัด → ถ้าไม่มี audit trail จะโยนความผิดกันไปมา

🔁 Consistency & Over-reliance

ทดลองจริง: งานเดิม ตรวจ 3 รอบ คะแนนรวม 34 → 34 → 30 (แกว่ง 4 คะแนนเต็ม) — ไม่ยุติธรรมต่อนักเรียนคนเดียวกัน และเมื่อระบบแกว่ง ครูอาจยิ่งพึ่ง AI เพราะ "ขี้เกียจตรวจเอง" แทนที่จะทบทวน

04แนวทางแก้ไข/ป้องกัน ถ้าเราพัฒนาแอปนี้จริง

ประเด็นแนวทางแก้ไขตัวอย่างรูปธรรม
Bias / Fairnessทดสอบอคติด้วยชุดข้อมูลหลากหลายก่อนปล่อยใช้งาน (bias audit) + ระบุใน prompt ห้ามตัดสินจากสไตล์ภาษา + ให้คะแนนแยก "เนื้อหา" ออกจาก "ภาษา" เสมอตรวจ essay เดียวกันที่เขียนโดยเจ้าของภาษา/ไม่ใช่เจ้าของภาษา เทียบคะแนน — ถ้าต่างอย่างมีนัยสำคัญ ต้องจูน rubric ก่อนเปิดใช้
Hallucinationบังคับ evidence-based grading: ทุกคะแนนต้อง quote ข้อความจริงจากงาน + ระบบตรวจกลับอัตโนมัติว่า quote มีอยู่จริงในต้นฉบับทำแล้วในแอป — ถ้า evidence ไม่พบในข้อความต้นฉบับ ระบบขึ้นธง ⚠ ให้ครูตรวจสอบ
Transparencyเปิดเผย rubric + เหตุผลรายเกณฑ์ให้ผู้เรียนดูได้ทุกเมื่อ + มีช่องทางอุทธรณ์ทำแล้วในแอป — Transparency panel แสดง prompt จริง + คะแนนนักเรียนกดดูเหตุผลรายข้อได้
Privacy / PDPAไม่เก็บงานนักเรียนบนเซิร์ฟเวอร์ (stateless) + key อยู่ฝั่ง proxy + anonymize ก่อนส่ง + ขอความยินยอมชัดเจนทำแล้วในแอป — ข้อความถูกส่งตรงแล้วทิ้ง ไม่ลง DB; โรงเรียนใหญ่ควรใช้ on-premise model แทน API ภายนอก
AccountabilityHuman-in-the-loop บังคับ: AI เป็น "ผู้ช่วย" ไม่ใช่ "ผู้ตัดสิน" + Audit log ทุกการแก้คะแนนพร้อมเหตุผลทำแล้วในแอป — Teacher Override บังคับกรอกเหตุผล มิฉะนั้นบันทึกไม่ได้
Consistencytemperature ต่ำ + ตรวจหลายรอบใช้มัธยฐาน + แจ้งผู้ใช้ตรง ๆ ว่าระบบมีความแปรปรวนเท่าไรทำแล้วในแอป — Consistency Check ×3 แสดงส่วนต่างพร้อมคำแนะนำ

05เราใช้ Vibe Coding สร้างแอปอย่างไร (ลำดับ prompt จริง — แอปนี้ถูก vibe code ทั้งโปรเจกต์)

ลำดับการทำงาน

  • 1. ป้อนโจทย์ — ส่ง PDF ใบงาน + ไอเดียที่เลือกให้ AI agent (Hermes Agent + Qwen 3.8 Max)
  • 2. ให้ agent วางแผน — เสนอสถาปัตยกรรม: static web app + local proxy (Python stdlib) + Demo Mode
  • 3. Agent เขียนโค้ดทั้งโปรเจกต์ — HTML / CSS / JS 3 ไฟล์ / serve.py โดยเราไม่ได้พิมพ์โค้ดเองเลย
  • 4. Agent ทดสอบตัวเอง — เรียก API จริง + ขับเบราว์เซอร์ headless (CDP) กดทุก flow + ตรวจ screenshot ว่าภาษาไทย render ถูก
  • 5. เจอบั๊กจริง → แก้ — โมเดล reasoning เผา token budget กับการ "คิด" จนได้คำตอบว่างเปล่า → เพิ่ม max_tokens + auto-retry
  • 6. Deploy — git push → GitHub Pages อัตโนมัติ

เครื่องมือ

Hermes AgentQwen 3.8 MaxVanilla HTML/CSS/JSPython stdlib proxyGitHub Pages

Prompt หลักที่มนุษย์พิมพ์จริง

"i need to made an app for this i think web app
 would work what you think"

"can you plan it out and do the whole thing for me"

ที่เหลือ agent ต่อยอดเองทั้งหมด: ออกแบบ UI, เขียน prompt engineering ของระบบตรวจ (rubric prompt, JSON schema, evidence rule), ทดสอบ, แก้บั๊ก, deploy

ผลลัพธ์

เว็บแอปทำงานได้จริงครบทุก flow ภายในเซสชันเดียว — ถ้าเขียนเองตามวิธีดั้งเดิม (ออกแบบ UI, เขียน backend, ทดสอบ, deploy) อาจใช้เวลาหลายวัน

สิ่งที่มนุษย์ยังต้องทำ

  • ตัดสินใจเลือกไอเดียและยืนยันสถาปัตยกรรม
  • ตรวจสอบว่าผลตรวจของ AI สมเหตุสมผล (อ่าน evidence ด้วยตา)
  • รับผิดชอบต่อสิ่งที่ deploy ออกสู่สาธารณะ

→ แก่นของ vibe coding: มนุษย์ย้ายจาก "คนเขียนโค้ด" เป็น "คนกำกับและรับผิดชอบ"

06Vibe Coding ก่อให้เกิดประเด็นจริยธรรมในการพัฒนาโปรแกรมอย่างไร (จากประสบการณ์ตรงของโปรเจกต์นี้)

1 · นักพัฒนาไม่เข้าใจโค้ดที่ตนปล่อยออกไป

โค้ดถูกสร้างเร็วเกินกว่าจะ review ทัน — เราไม่เคยอ่าน serve.py ทั้งไฟล์ก่อน deploy ถ้ามีช่องโหว่ (เช่น key รั่ว, injection) ผู้ใช้จริงคือเหยื่อ ทั้งที่ไม่มีใครตั้งใจเขียนบั๊ก → คำถาม accountability: ใครรับผิดชอบโค้ดที่มนุษย์สั่งให้เกิดแต่ไม่เคยอ่าน?

2 · ความปลอดภัยถูกแลกกับความไว

ตัวอย่างจริงจากโปรเจกต์: agent เผลอ commit ไฟล์ log เข้า git repo สาธารณะรอบแรก (ไม่มี key แต่สะท้อนว่า vibe coding ทำให้ "พลาดแล้วเผยแพร่" เกิดง่ายมาก เพราะทุกอย่างเร็วและอัตโนมัติ) — ถ้าพลาดเป็นไฟล์ key.txt ผลคือ key รั่วสู่สาธารณะทันที

3 · อคติของโมเดลถูกฝังลงในผลิตภัณฑ์โดยไม่รู้ตัว

AI เขียนทั้ง UI copy, rubric, prompt วิศวกรรม — ค่านิยมที่แฝงในข้อมูลฝึกของโมเดลถูกส่งต่อให้ผู้ใช้ปลายทางโดยไม่มีใครกรอง เช่น การเลือกเกณฑ์ให้คะแนนแบบไหน "ดี" ก็ถูกตัดสินโดยโมเดลตั้งแต่ต้น

4 · ทักษะนักพัฒนารุ่นใหม่ถูกกัดกร่อน

ถ้าเด็ก CS พึ่ง vibe coding ตั้งแต่เรียนปี 1 จะไม่ผ่านการฝึก debug/ออกแบบด้วยตัวเอง — ระยะยาวอุตสาหกรรมได้ "ผู้กดปุ่ม" ที่แยกแยะโค้ดดี/เลวไม่ได้ ซึ่งเป็นอันตรายเมื่อระบบที่ต้องรับผิดชอบมีผลกระทบต่อชีวิตคน

5 · ผลงาน/ลิขสิทธิ์กำกวม

โค้ดที่โมเดลเขียนอาจคล้ายโค้ดมีลิขสิทธิ์จากข้อมูลฝึก โดยไม่มีใครรู้ — ใครเป็นเจ้าของแอปนี้? คนสั่ง? บริษัทโมเดล? และถ้าแอปทำรายได้ ลิขสิทธิ์อยู่ที่ใคร (ปัจจุบันกฎหมายยังไม่มีคำตอบชัด)

แนวทางของเรา: Vibe Coding อย่างรับผิดชอบ

  • ใช้ agent เขียน แต่ทดสอบทุก flow ด้วยตัวเอง/ด้วยเครื่องมืออัตโนมัติก่อนส่งมอบ
  • ความลับ (API key) ต้องอยู่นอกโค้ดที่ commit เสมอ + ตรวจ git ก่อน push
  • เปิดเผยในสไลด์ตรง ๆ ว่าส่วนไหน AI ทำ ส่วนไหนมนุษย์ตัดสินใจ
